# Encrypted attachment profile: a bounded comparison

[Issue #247](https://github.com/gonz0w/faction-bbs/issues/247) · 2026-10-27 · Research owner: Faction maintainers

**Question:** Which specified format and smallest independent proof could establish a defensible starting point for device-encrypted private-mail attachments? This source comparison ends with an experiment proposal, not format, dependency, transport or product adoption. The original requirements remain in [#88](https://github.com/gonz0w/faction-bbs/issues/88).

The decision rule favors a specified reusable encryption and metadata format with an inspectable independent implementation, keys and private metadata within authenticated member-device E2EE, bounded streaming, and transport separation. Independent encrypted interoperability and authenticated private storage are gates, not assumptions. No candidate clears all gates today. No numerical ranking is useful while these gates remain unknown.

## Primary profiles and observations

The following official specifications were retrieved 2026-10-27. Their versions and status describe the sources, not Faction conformance.

| Profile | Source observation | Implication for the question |
| --- | --- | --- |
| [XEP-0446](https://xmpp.org/extensions/xep-0446.html) v0.2.0, Experimental, 2022-07-17 | File metadata including size and hashes. | Useful structured metadata; its privacy depends on placement. |
| [XEP-0447](https://xmpp.org/extensions/xep-0447.html) v0.3.1, Experimental, 2024-01-01 | File sharing combines metadata and sources. | A descriptor can separate a file from its transport. |
| [XEP-0448](https://xmpp.org/extensions/xep-0448.html) v0.2.0, Experimental, 2022-07-17 | An encrypted source carries key and IV, with original size and hash required; end-to-end encrypted sharing requires the XML itself to be E2EE, although the specification also describes a trusted-intermediary use without it. CBC is permitted; an authentication tag for GCM is recommended. Receive guidance describes trimming excess bytes. | Strict authenticated GCM and exact-size rejection would be a narrower profile requiring compatibility proof, not a claim about every valid 0448 sender. |
| [XEP-0454](https://xmpp.org/extensions/xep-0454.html) v0.1.0, Historical type, Experimental status, 2021-01-26 | AES-256-GCM uses a 32-byte key, 12-byte IV and appended tag; the encrypted message carries a URL fragment containing IV then key. | Useful historical byte-level comparison, but alone it does not establish the private filename, hash and size contract. It is not the 0448 profile. |
| [XEP-0384](https://xmpp.org/extensions/xep-0384.html) v0.9.1, Experimental, 2026-04-06; [XEP-0420](https://xmpp.org/extensions/xep-0420.html) v0.5.0, Experimental, 2026-06-23 | Current OMEMO and SCE specifications. | Faction implements a reviewed narrow subset, not every current XML extension. |
| [XEP-0363](https://xmpp.org/extensions/xep-0363.html) v1.2.0, Stable, 2025-06-17 | Knowledge of the URL SHOULD permit fetching an uploaded file. | The upload specification does not itself require recipient authentication or a private portal. |

Source observations have high confidence for the cited versions; the fit and compatibility implications are inferences with moderate confidence until tested. A spec's encryption vocabulary does not establish interoperability or safe storage.

### Implementations inspected

These are source/release observations, not compiled programs or exchanged files. Versions identify the inspected sources; the project has not selected them as dependencies.

- [QXmpp v1.17.0](https://github.com/KDE/qxmpp/tree/86431213cbd4f5e1a70bd9c7a7db197006cf4c29), released 2026-10-06, requires Qt 6.4 or later; its encryption features require OpenSSL 3 or later (optional for QXmpp overall). Its [source license](https://github.com/KDE/qxmpp/blob/86431213cbd4f5e1a70bd9c7a7db197006cf4c29/LICENSES/LGPL-2.1-or-later.txt) is LGPL 2.1+; encryption binaries have effective LGPL 3+ terms, and use with libomemo-c is GPL 3. The [encrypted sharing provider](https://github.com/KDE/qxmpp/blob/86431213cbd4f5e1a70bd9c7a7db197006cf4c29/src/client/QXmppEncryptedFileSharingProvider.cpp) defaults to AES-256-CBC with PKCS7 and uploads an opaque filename and `application/octet-stream`. [Encryption source](https://github.com/KDE/qxmpp/blob/86431213cbd4f5e1a70bd9c7a7db197006cf4c29/src/client/QXmppFileEncryption.cpp) also supports GCM. [Sharing manager](https://github.com/KDE/qxmpp/blob/86431213cbd4f5e1a70bd9c7a7db197006cf4c29/src/client/QXmppFileSharingManager.cpp) hash checks depend on the output path. Its [crypto source](https://github.com/KDE/qxmpp/blob/86431213cbd4f5e1a70bd9c7a7db197006cf4c29/src/base/Crypto.cpp) omits GCM tag generation and verification and skips GCM finalization; its [self-roundtrip test](https://github.com/KDE/qxmpp/blob/86431213cbd4f5e1a70bd9c7a7db197006cf4c29/tests/FileSharing.cpp) uses a 32-byte IV. It is a profile comparator, not an unchanged strict-GCM oracle. These observations alone do not establish a vulnerability without analyzing the trusted hash envelope.
- [Kaidan v0.16.0](https://www.kaidan.im/2026/07/21/kaidan-0.16.0/) uses the [QXmpp provider](https://github.com/KDE/kaidan/blob/542320ae59b619c7598ed5bf50f14965afdc3d40/src/FileSharingController.cpp); it is not a second independent implementation. Its GPL 3+ Qt/QML/Quick stack is not proposed for product reuse.
- [Gajim 2.4.7](https://github.com/gajim/gajim/tree/c9b40e5e220ea59b0e387ac3e753eac1cfe215a1), [GPL 3 only](https://github.com/gajim/gajim/blob/c9b40e5e220ea59b0e387ac3e753eac1cfe215a1/COPYING), uses Python cryptography in its [AES](https://github.com/gajim/gajim/blob/c9b40e5e220ea59b0e387ac3e753eac1cfe215a1/gajim/common/aes.py) and [HTTP upload](https://github.com/gajim/gajim/blob/c9b40e5e220ea59b0e387ac3e753eac1cfe215a1/gajim/common/modules/httpupload.py) sources. It is an independent legacy AES-GCM reference for a byte proof, not evidence of modern 0447/0448 descriptor interoperability.
- [Dino 0.5](https://dino.im/blog/2025/04/dino-0.5-release/) explicitly describes unencrypted 0447 support pending SCE. It is not evidence of encrypted interoperability.

## Privacy and current boundaries

The candidate would encrypt file bytes on the member device with a fresh attachment key. A structured descriptor inside authenticated OMEMO/SCE would contain the key, IV, private filename and media type, original size/hash and an untrusted locator. Neither the visited BBS nor ordinary SSH receives plaintext or keys. A home routes ciphertext and observes addressing, timing and sizes; ciphertext storage sees opaque bytes, locator and access metadata. Encryption does not hide all traffic metadata, prevent a recipient retaining a copy, or make a locator trustworthy. Fetching requires destination, redirect, time and size bounds and a verified recipient; authenticated private access is a separate design gate.

The current [SCE and checkpoint contract](../native-mail-checkpoints.md) accepts subject and body, rejects unknown extensions and persists text intent, history and immutable outbound ciphertext atomically. [SCE source](../../crates/faction-omemo/src/sce.rs) and [checkpoint source](../../crates/faction-client/src/mail_checkpoint.rs) are the implementation boundaries. Adding a typed descriptor and its durable intent/history would require an explicit compatible version and transaction design; hiding a key-bearing URL in body text would expose it to the current display. The [native device interface](../../crates/faction-omemo/src/native.rs) handles bounded opaque messages, not a streaming blob. One verified peer is supported. Picomemo is locally corrected 1.3.1, not unchanged upstream. A checkpoint transaction cannot atomically commit an external blob, and history backup cannot recover a missing blob.

Existing community [SFTP](../../crates/faction-client/src/sftp.rs) uses sysop-readable grants, not a private attachment namespace; its transfer limits are not attachment limits. Its temporary-file and no-overwrite pattern may inform a later save design. Private HTTPS is closest to the examined clients' upload model, but recipient authorization, destination allowlists, redirects and expiry remain separate questions. SFTP needs separate opaque namespace and grants. Jingle introduces session state and offline retention concerns and is not the first proof.

## Gate judgment and experiment proposal

| Gate | Judgment and reason |
| --- | --- |
| Private content and metadata | Structurally promising only: 0447/0448 can place metadata and keys in authenticated SCE. Actual strict decoding, leakage and recipient checks are unproven. |
| Authenticated cipher and exact length | Open: 0448 allows CBC and its receive guidance differs from a proposed strict GCM/exact-size subset. |
| Independent encrypted interoperability | Open: QXmpp source supports encryption; Gajim is a legacy byte reference and Kaidan shares QXmpp. No file was exchanged here. |
| Streaming, NetBSD and dependencies | Open: current message API is not a blob stream; licenses, vetted primitive/API and target support require separate qualification. |
| Private transport and durable recovery | Open: URL possession is not recipient authorization; external blob publication and local key/checkpoint durability are not one transaction. |

The [decision framework](decision-framework.md) gates map as follows: G1 no-JS and G9 license/dependency closure remain unknown for the exact proof graph; G2/G3 local approval and identity are not imported, and recipient proof is unknown. G4/G6 propose a local spool without adopting HTTP or a provider. G5 privacy is unproven; G7 classic access remains unchanged; G8 is not applicable because no extension runtime is adopted. These are scope judgments, not runtime passes.

**Propose an experiment**, with moderate confidence in the structural fit and low confidence in interoperability and operational feasibility. Use 0447 plus 0448 metadata inside authenticated OMEMO-2/SCE as the candidate to investigate, not an adopted profile. The owner or authorized maintainer decides any material adoption after review. Reversal of this research choice is low cost because no persistent format or service changes here; adopting a wire format, stored state or service would have higher reversal cost and require migration and recovery evidence. A demonstrated incompatibility, unsafe metadata exposure, unworkable private authorization or durable-state failure reopens the choice.

The first proposed proof is reciprocal exchange of one opaque file through a local ciphertext-only spool, with no HTTP service. Compare unchanged Gajim 2.4.7 AES-GCM as an isolated GPL research reference with a small separate research adapter over OpenSSL EVP. The proposed native input is OpenSSL 3.5.7, annotated tag `6ca677c395a4ae4472a12c5857c122ec33b36f66`, commit [`8cf17aaeb4599f8af87fefd810b5b5fee90fe69e`](https://github.com/openssl/openssl/tree/8cf17aaeb4599f8af87fefd810b5b5fee90fe69e), Apache 2.0. Its [AES-GCM demo](https://github.com/openssl/openssl/blob/8cf17aaeb4599f8af87fefd810b5b5fee90fe69e/demos/cipher/aesgcm.c) illustrates fetched AES-256-GCM, 12-byte IV, 16-byte tag and the decrypt-final API; it was not run and is not itself the 0454 wire profile. The demo prints plaintext before finalization and reports the verification result without propagating failure. Gajim also returns update plaintext before tag finalization. A new test-first research adapter must quarantine update output, discard it on failure, and reject a nonpositive final result before any plaintext save; neither reference alone establishes this behavior. The byte proof must use empty AAD. A previous reference used cryptography 50.0.2, host macOS ARM wheel SHA-256 `fa8f5efb344d6908a1ce62f4a24e2e5780f825d6f53f5f50ec5ffacac72936cb`, Apache 2.0 or BSD 3-Clause; [the historical result](../evidence/omemo-interop/results.json) does not establish present availability or select a product dependency. Before execution, pin the complete selected graph, toolchain, no-JS closure and bounds, and stop if unavailable. These are independent application adapters and byte formats, not necessarily independent cryptographic primitives: Python cryptography may use OpenSSL too. Do not describe byte compatibility as full modern Gajim descriptor interoperability. Independently test descriptor semantics against the selected 0447/0448 subset. This is a proposed finite test matrix, not an executed test or a commitment to implement it:

| Phase | Inputs and positive observation | Negative observation required |
| --- | --- | --- |
| Blob bytes | Public key `00..1f`; 12-byte IV of eleven zero bytes followed by the zero-based case index; empty AAD; synthetic bytes `i mod 256` at lengths 0, 1, 15, 16, 17, 4095, 4096 and 4097. Check overflow and ciphertext length `n + 16`, exact ciphertext bytes and reciprocal plaintext. These fixtures are not a product cap, streaming or performance claim. | Wrong key, flipped tag or ciphertext bit, truncation and appended bytes reject before plaintext save. Characterize Gajim retained-tag-cache segmentation at 1, 15, 16, 17 and 4096 separately; preserve failures without patching the reference. |
| Descriptor | Synthetic structured descriptor, verified peer and bounded locator; required size/hash and cipher match authenticated bytes. | Wrong size/hash, unknown cipher, missing authentication and wrong/unverified recipient reject before plaintext save. |
| Local spool and save | Only ciphertext in a disposable local spool; explicit confirmation and no-overwrite destination. Inspect spool and logs for no private keys, names or plaintext. | Existing destination, cancellation or failed verification leaves no accepted plaintext or overwritten file. |
| Later transport and durability | Separate authorized proof of private retrieval, offline/retry and transaction/recovery with bounded quotas. | Denied/expired access, disconnect, disk full, orphaned blobs and interrupted or ambiguous commits remain visible and recoverable under a defined contract. |

Future work must also cover two independent homes, retry/deduplication, storage quotas, backup and password-reset limits, revocation and old recipient copies, and the remaining parent acceptance. No local spool result would prove remote recipient authorization, real-network interoperability, complete SCE conformance, hardware capacity or production readiness. Rust, primary NetBSD, no JavaScript, device-private keys, classic access, existing resource limits and the stopped playground remain unchanged.
