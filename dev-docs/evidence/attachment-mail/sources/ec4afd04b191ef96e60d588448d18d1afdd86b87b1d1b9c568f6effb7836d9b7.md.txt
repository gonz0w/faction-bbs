# Experimental attachment bytes and explicit save

These native-only member-device library primitives encrypt and verify bounded attachment bytes and save an already verified value to a caller-selected local file. They do not deliver attachments. The [candidate metadata codec](attachment-metadata.md) is separate; existing text SCE APIs reject its attachment extension. The explicitly enabled [attachment mail](attachment-mail.md) checkpoint accepts and retains descriptors.

## Encrypt and verify

With the `faction-omemo` `native` feature, `blob::encrypt` accepts at most 1,048,576 plaintext bytes in a complete buffer. Each call generates a fresh 32-byte key and 12-byte IV. AES-256-GCM uses empty associated data and appends a 16-byte tag, so ciphertext is at most 1,048,592 bytes. The returned ciphertext, key, IV, SHA-256 hash and exact plaintext size let a trusted caller construct the candidate descriptor. The key, IV and hash use zeroizing storage. The bound is an experimental library limit, not a transport quota or streaming promise.

Before `blob::verify`, the caller must authenticate the descriptor in its sender/recipient SCE envelope and validate its bindings. Verification checks descriptor validity and bounds, authenticates the ciphertext, and requires the exact declared plaintext size and SHA-256 hash. Only then does it return an opaque `VerifiedBlob` with immutable `as_bytes` access and zeroizing owned plaintext. The type proves bytes against supplied metadata; it does not establish sender or recipient identity, authorize a locator, or fetch anything. Blob-only entry also checks OpenSSL major 3 and core-dump suppression before allocating new secret buffers. Zeroization does not promise erasure of every operating-system or parser copy.

## Save and recovery

With the `faction-client` `native-mail` feature, `attachment_save::save_verified` accepts only a `VerifiedBlob` and an explicit absolute destination selected by the trusted local caller. Cancellation means making no save call. Metadata never selects the destination. The existing final parent must be owned by the effective UID and have exact mode `0700`; parent components are opened relative to directory descriptors with `NOFOLLOW`, and traversal and symlink ancestors are refused. This does not isolate hostile root, other processes with the same UID, or ACL access.

The operation creates a random exclusive `0600` temporary file in that parent, writes and syncs the verified bytes, then uses descriptor-relative `linkat` to publish without replacing an existing destination. It removes only its identified temporary inode and syncs the directory. Existing or racing destination objects are not overwritten. `BeforePublication` identifies failures before publication or a definite destination collision. Once publication is attempted, other link errors and later failures report `PublicationUncertain`: the destination may contain the complete verified file, so inspect it before retrying. The operation never removes the destination to simulate rollback. Failed or interrupted operations can leave private temporary files; inspect and deliberately remove owned leftovers when appropriate. There is no automatic sweep, secure-erasure or power-cut guarantee, and remote filesystems have not been qualified for universal error-return behavior.

## Observations and limits

Focused host checks observed 21 native library passes, five blob-contract passes, two guard parent passes plus the actually invoked isolated core-guard child, and one native peer/blob pass. Runtime-major-4 and core-refusal cases are simulated test controls. C warnings-as-errors/static analysis and Clippy passed. The latest save checks observed eight private and four public passes, including a real peer descriptor through blob verification to an explicit file, restrictive child umask, and publication-error classification. The [evidence record](evidence/attachment-blobs-save/README.md) records actual host checks and their limitations.

One 1 MiB cap observation on a single host in a debug test process reported 8,552,448 bytes process RSS, 8.614 ms encryption and 0.544 ms verification. The process includes the test harness, fixtures and library; this is neither per-call allocation nor whole-host capacity evidence. Original executed inputs and logs are retained for review.

The opt-in checkpoint retains attachment descriptors and keys in encrypted history; the existing `network-mail` adapter can deliver their messages. There is no attachment UI, bulk-byte transport, fetch or upload, private server storage, or modern-client interoperability qualification. No NetBSD replay or whole-host capacity support follows from these host observations. Parent [#88](https://github.com/gonz0w/faction-bbs/issues/88) remains open.
