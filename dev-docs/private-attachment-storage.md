# Private ciphertext storage and transfer

The experimental, default-off native library path transfers ciphertext through deliberately invoked bounded cycles. It uses the existing pinned XMPP home session for the sender's own home and an explicit invited-home route for the authenticated sender when a recipient fetches. A locator never grants a destination or establishes trust. This is a library and home handler contract, not a stock Prosody provider/plugin or deployment; it starts no UI, CLI, listener, host, VM or playground.

## Member-device sequence

`mail_blob_transfer::Spool::open` opens a separate member-local ciphertext directory. `prepare` takes a `Selection` of bytes and private metadata plus an operation ID; it encrypts selected bytes on the member device with a fresh attachment key and IV, then durably spools ciphertext before queuing the existing encrypted descriptor and exact wire. The descriptor carries the key and private metadata only in encrypted checkpoint history. `upload_cycle` calls resume bounded upload, commit the exact ciphertext length and digest, then send the persisted wire using a fresh authenticated session. A network write does not itself acknowledge or reseal the message. Ordinary Sync cannot bypass upload ordering for the private identifier; existing text and HTTPS behavior remain. Each cycle handles at most four 4096-byte chunks and at most eight storage IQ requests; release may add pubsub requests. Each public upload or fetch call has a cooperative ten-second timeout across the whole call, including both sequential sessions when upload completes. Each session independently retains the 16 KiB stanza, 64 KiB physical input and 256-event limits; these are not aggregate per-call limits. There is no background reconnect loop. A crash before queueing can leave a bounded opaque spool orphan whose digest is absent from mail history. There is no inventory UI or automatic sweep; `Spool::delete` retires an object only when its digest is known. Inspect storage and backups deliberately for retention and recovery; spool and vault are not one crash transaction. Spool expiry still applies; the older caller-supplied ciphertext APIs retain their separate historical consumption behavior.

`fetch_cycle` takes a `ReceivedSelection` containing a retained record index and frame identity, and begins with the authenticated received record and its sender binding, uses the selected invited route, and stores ciphertext privately on the recipient device. `verify_fetched` checks against that record's descriptor; `save_fetched` verifies before an explicit save to a caller-selected absolute path; completion never chooses a path, opens, executes or extracts content. [Safe save](attachment-blobs-save.md) describes no-overwrite and publication uncertainty. Historical locally supplied ciphertext remains usable under the earlier [attachment mail](attachment-mail.md) contract. The exact identifier is `urn:faction:blob:1:<64 lowercase hexadecimal ciphertext SHA-256>`; older HTTPS locators remain inert and do not trigger this path.

## Store and authority

The ciphertext store allows at most eight objects, including incomplete uploads, each at most 1,048,592 ciphertext bytes and 8,388,736 bytes total, with 4096-byte chunks and retention no longer than seven days. Expiry is immutable; retries do not renew it. A persisted high-water clock rejects rollback. Successful operations and authorized observations of expiry advance it durably, preventing an observed expiry from being revived by clock rollback; policy denials do not advance it. Exact retries are deduplicated; commit checks length and SHA-256 before recipient reads. Current authorization and invited-peer policy are checked on each operation. Expired objects remain charged until the sender deliberately deletes them under current policy; deletion and expiry cannot revoke a copy already downloaded by a recipient. `Store::open` holds an exclusive lock and `Store::dispatch` takes a separate trusted actor and `Access` policy. After a storage error the store requires reopening; after `PublicationUncertain`, inspect the reopened state rather than assuming rollback.

The `mail_blob_wire` IQ codec wraps bounded requests and responses and returns uniform remote failure responses without exposing error or existence classes; an embedding home handler must authenticate separately and call the store. The handler requires an external trusted principal and current account/device/full public identity and invited-peer policy. Neither stanza claims nor a SASL resource provide device attestation. No server holds keys, private filename, subject or content text; it can see account, device, public identity, ciphertext digest and size, time and access patterns. Encryption does not provide anonymity. The local spool and server store use private owned storage. Successful operations and authorized expiry observations with increasing timestamps, including reads and status, rewrite the whole snapshot. A snapshot is capped at 8,396,928 bytes including metadata; snapshot and pending file together allow 16,793,856 regular-file content bytes, plus a permanent zero-length lock. Filesystem blocks, journals and metadata are additional. Reopening under the lock removes a stale owned pending file; unexpected directory entries refuse opening. Operators must account for this write amplification and space, and retain or delete backups deliberately. The store's retention bound does not erase copies in backups.

This batch does not establish deployed provider behavior, independent modern-client interoperability, fresh NetBSD qualification, physical hardware or 250-user capacity. Independent home BBS admission still requires its own approval. Classic access and text mail remain available; the broader original attachment requirements remain in [#88](https://github.com/gonz0w/faction-bbs/issues/88).
